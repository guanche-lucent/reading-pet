## ⚠️ 先说第 1 件：这不是选型问题，是我们之前定的规则**自相矛盾**

**矛盾在哪：**

| 我们定的 | 实际数字 |
|---|---|
| 原文与解析全文 **7 天后删除** | 在一本 20 万字的书上，每天读 5 分钟 ≈ 1200 字 → **读完要 160 多天** |
| 任务卡要带一段**原文节选**给用户读 | 第 7 天以后原文没了，**卡就没内容可读了** |
| 每天出一张卡 | 7 天最多出 7 张卡，一本书需要 50–200 张 |

也就是说：**照现在的规则，用户第 8 天就没法继续读了。** 这不是 bug，是"7 天删原文"和"读完一本书"这两条规则撞在一起。

（注意：我们的成功指标是"7 天内完成 3 张卡"，这个不受影响；受影响的是"把一本书读完"这个产品承诺。）

### 三个选择

| 选项 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A（推荐）** | **滚动续期 + 到期转复习卡**：①原文到期时间改为"最后一次阅读活动 + 7 天"（在读就一直续，停读 7 天才删）；②到期的卡不再显示原文节选，改用**长期保留的关键点**出"复习卡"（"用你自己的话讲一遍这个观点"） | 用户能读完一本书；隐私承诺仍然成立（停读 7 天必删）；到期后仍能复习 | 需要在 `books` 加"最后活动时间"字段；卡片模板要分两种（带节选 / 复习型） |
| B | **延长到"读完为止 + 最长 60 天"** | 实现最简单，不用改卡片模板 | 隐私承诺要改口（用户可能一本书挂 2 个月）；仍是硬到期，没读完就断 |
| C | **维持硬 7 天** | 最严格，不用改任何设计 | 一本书永远读不完；用户必须反复重新上传、系统反复重新外发确认——体验和成本都最差 |

**我的推荐：A**。它同时满足"能读完"和"停读就删"，只是把 7 天的意思从"上传后 7 天"改成"停读 7 天"。

**影响哪些表**：`books` 加 `last_reading_activity_at`、`originals_expire_at` 改为滚动计算；`task_cards` 加 `card_kind`（`excerpt` / `review`）。

## 第 2 件：账号怎么登？

- **A（推荐）邮箱 + 密码**（自己存哈希，不接第三方）：零外部依赖，10 个测试用户够用；二期再换微信/Apple。
- B 邮箱 + 一次性验证码：体验更好，但要先接一个邮件发送服务。
- C 第三方登录（微信 / Apple）：体验最好，但要资质、要审核，首轮不划算。

**影响**：`accounts.login_type` 取值、登录端点、是否需要存密码哈希列。

## 第 3 件：数据库与文件存储放哪？

- **A（推荐）云数据库 PostgreSQL（大陆区域）+ 云对象存储（同区域，开 7 天生命周期规则兜底）**：与 v3.1 一致，延迟低，合规简单。
- B SQLite + 本机目录：只能自己电脑上玩，10 个真人用户不能这么做。
- C 云数据库 + 自建 MinIO：多一套运维，首轮不值。

**影响**：DDL 语法、生命周期规则写法、部署脚本。

## 第 4 件：模型用哪个、成本上限多少、能等多久？

- **A（推荐）全部用 `deepseek-flash`**（你平台现成、100 万上下文、便宜）：拆书、出题、判定都用它；草图不用模型（走预置素材）。**单本上限 20 万 token；用户点击到出卡 ≤ 90 秒**（异步，页面显示进度）。
- B 拆书用 `deepseek-v4-pro`、判定用 flash：质量更高，成本大约翻倍。
- C 本地模型：省调用费，但质量、显存、运维都要自己扛。

**影响**：`judgements` 的成本字段、`job_queue` 的超时与重试上限、限流策略。

## 第 5 件：宠物素材先做多少？

- **A（推荐）4 个宠物状态 × 3 个房间主题 ≈ 12 张静态图 + 6 个内容标签**（认知 / 情绪 / 方法 / 故事 / 数据 / 关系）：够验证"内容影响宠物"这个卖点，又不会画太多。
- B 只做 1 个房间 4 个状态（4 张图）：最省，但看不出"房间随书变化"。
- C 一次做 20+ 张：还没验证就要画一堆，白画风险高。

**影响**：`pet_asset_map` 的数据量、素材包命名、UI 里房间切换。

## 第 6 件：判定为「存疑」的谁来复核？

- **A（推荐）你自己每周看一次队列**（约 10–20 条），只标"判对了/判错了"，用来调提示词。首轮样本小，够用。
- B 不复核：护栏指标（复述有效性 ≥70%）会失真，等于白测。
- C 找第三方标注：质量高但要花钱、要沟通，首轮不值。

**影响**：`manual_review_queue` 的运营流程、是否需要最小的复核页面。

## 第 1 件补充：停读 7 天后用户回来，会发生什么

**被删的只有两样**：PDF 原文、解析出来的逐段全文。
**留下的有**：任务卡（题干 + 关键点）、复述与判定、阅读进度、宠物状态、记忆（已掌握 / 易忘）。

用户第 8 天打开时，看到一条说明 + 三条路：

1. **继续复习**：已有卡片照常打开（复习型卡："用你自己的话讲一遍这个观点"），**不用重新上传任何东西**。
2. **接着往下读**：点"继续这本书" → 重新选同一个 PDF → 系统用**文件指纹（sha256，`books.file_sha256`）**认出"还是这本书" → **沿用原来的进度、关键点、宠物**，只解析还没读的部分（**不用从第 1 页重来**）。外发确认沿用原凭据，但会明确提示"这本书你之前同意过外发，继续沿用？"，可随时撤回。
3. **不读了**：一键删除，连进度与宠物记忆一起清。

一句话：**丢的只是原文，不丢进度、不丢宠物、不用从头开始。** 上传的是另一本书（指纹不同）则当新书处理。

## 第 3 件补充：云数据库怎么收费

计费维度（都按这个公式叠加）：

| 维度 | 说明 |
|---|---|
| 计算规格 | CPU + 内存，如 1 核 2G；按月（包月）或按小时（按量） |
| 存储空间 | 按 GB/月，如 20GB |
| 备份空间 | 超出赠送额度后按 GB/月 |
| 网络 | 公网流量按 GB；内网（同区域）通常免费 |
| 计费方式 | 包月比按量便宜；按量适合短期 |

**典型区间（我 curl 抓不到实时价，官网是动态渲染；下表需以官网为准）**：

| 方案 | 估算 | 说明 |
|---|---|---|
| 托管云数据库 PostgreSQL，最小规格（1核2G / 20GB） | **约 60–150 元/月** | 免运维、自带备份，最省心 |
| 一台轻量云服务器（2核2G）自装 PostgreSQL | 约 24–60 元/月 | 便宜，但备份、升级、故障要自己管 |
| 对象存储（存 PDF） | 20MB ≈ **几分钱/月** | 存储极便宜，流量另计（几毛/GB） |
| 本机 / Docker 跑 PostgreSQL | **0 元** | 只适合自己先验证，真人用户不能用 |

**10 个用户的规模，上云一个月 100 元以内够用。**

## 第 5 件补充：要不要加宠物配饰

**素材数量是"乘"出来的**：4 状态 × 3 房间 = 12 张；每加一类配饰都 ×N，白画风险高。

- **5A（推荐）**：只做 4 状态 × 3 房间 = 12 张，**不加配饰**。"内容影响宠物"靠房间主题已经能看出来。
- **5B（想加就选它）**：12 张 + **只加"阅读纪念物"一种**——每读完一本书得 1 个（书签 / 徽章）挂在房间里，首版先备 3 个。数量随读书量增长，不会组合爆炸，还顺手给"读完一本书"一个奖励。
- 5C：现在就上多种配饰（不推荐）。

## 第 6 件：用大白话重写一遍

用户写完复述，AI 要判断"他有没有提到本段的关键点"。有时候 AI 也拿不准（写得太短、太含糊），这时它会说**"存疑"**——不算失败、不扣分、宠物照样喂。

**问题**：这些"拿不准"的样本，得有人看看 AI 判得对不对。否则你最后看到的"复述有效性 ≥70%"可能是在统计一堆 AI 乱判的结果，**等于白测**。

- **6A（推荐）**：**你每周花 5 分钟**，打开一个列表（一周约 10–20 条），每条显示"用户的复述 + 本段关键点 + AI 的判定"，你点"判对了 / 判错了"。这些标记用来改提示词。
- 6B：谁也不看 → 那个 70% 不可信。
- 6C：找第三方标注 → 质量高，但要花钱沟通。

## 第 3 件·本地存储可行性（回答"能不能不上云"）

**能，技术上完全可行**，但有三件事必须接受：

| 代价 | 说明 |
|---|---|
| 数据丢了找不回 | 用户换手机、清浏览器数据、卸载 → 阅读进度和宠物**永久丢失**，你无法恢复 |
| iPhone 会自己清理 | Safari 对"长期未访问站点"的本地存储有系统级清理策略；用户停读一段时间回来，**数据可能已被系统清掉**（比我们的 7 天更不可控） |
| 你没法远程排错 | 首轮 10 个用户，出问题时你只能靠用户导出的诊断包，看不到现场 |

另外澄清一个容易混的点：**"存哪里"和"发给谁"是两件事**。拆书、出题、判定都要把书的内容发给模型服务（这是"处理过程中经过"，不是"长期保存"）。除非改用本机小模型（首轮质量与运维都不现实）。

### 三个选项

**3A+（推荐）云端托管 + 原文不保留——比原方案更隐私、更便宜**

- 用户上传 PDF → **立刻解析 → 原文立即删除**（原来打算存 7 天，现在一天都不存）
- 解析文本保留 7 天（滚动续期，即 1A）；卡片 / 关键点 / 复述 / 进度 / 宠物长期保留
- 对象存储基本不用 → 成本主要是数据库，**约 60–150 元/月**
- 隐私承诺更好："你的原书文件从不留存"；跨设备可用；你能远程排查问题
- 改动：`books` 去掉"原文对象 key 的保留"语义，对象存储只在解析瞬间做中转；其余表不变

**3B 全本地（原文与记录都放用户设备）**

- 成本 ≈ 0（只留一个不落盘的极简代理转发模型请求）
- 隐私最强：原文从不上云
- 代价：上面三条全中；客户端复杂度大增（浏览器里解析 PDF、IndexedDB 存储、导出/导入备份）；**工期至少多 2–3 周**
- 改动：`source_blocks`、`keypoints`、`task_cards`、`retellings`、`progress`、`pet_state` 全部搬到客户端；服务端只剩代理；账号体系可省

**3C 混合（原文在本地，云端只存轻量进度）**

- 本地存原文与节选；云端只存卡片 / 关键点 / 复述 / 进度 / 宠物（KB 级，10 个用户总量 < 10MB）
- 跨设备能接续；原文从不上云
- 代价：仍要在浏览器里解析 PDF；iOS 清存储时"轻量进度在云端"能救回来，但原文要重新上传
- 改动：`source_blocks` 移到客户端，其余同 3A+
